# Clientes HTTP entre servicios

Lo que aprendimos al leer las respuestas del payment-service desde ticket-service (#66, US-TKT-23). Visto con Spring Boot 4 y Mockito 5.

- **Un 2xx no siempre es un éxito.** Si el otro servicio puede responder con un estado final ya guardado, un método `void` del cliente toma cualquier 2xx como "salió bien". Payment responde 2xx con el pago `CANCELLED` cuando una anulación se cruzó con el cobro, y ticket-service lo registraba como aprobado. El cliente tiene que devolver el cuerpo y el que llama, mirar el estado. Ejemplo: `ticket-service/.../service/OrderPaymentService.java`, `endedWithoutCharge`.
- **Un 404 se distingue por su código de error, no solo por el status.** El `GlobalExceptionHandler` de `common` responde 404 `resource_not_found` ante una ruta que no existe, por ejemplo un servicio viejo sin el endpoint o una URL mal armada. Eso no significa lo mismo que el 404 del recurso, como `payment_not_found`, y confundirlos puede borrar un estado que hacía falta. Se lee el `ErrorDto` con `getResponseBodyAs`. Ejemplo: `ticket-service/.../service/PaymentAttemptResolutionService.java`, `isPaymentNotFound`.
- **Un método `void` que pasa a devolver algo rompe los `doNothing()` de Mockito.** Mockito rechaza `doNothing()` sobre un método que no es `void` ("Only void methods can doNothing()"), y el mock devuelve `null` por defecto. Si el cambio de contrato trata `null` como el comportamiento de antes, alcanza con pasar esos stubs a `doReturn(null)`, sin tocar ningún assert. Ejemplo: `PaymentClient.charge` y `OrderPaymentMySqlIntegrationTest`.
